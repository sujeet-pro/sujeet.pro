Designing a URL Redirection & Vanity URL Service

From an in-memory HashMap to multi-region edge routing, Bloom filter origin protection, async click analytics, and realistic AWS build-vs-buy economics in the AI era.

Quick Read · 3 Min Principal Engineer Summary

TL;DR: Start with an edge-cached key-value map. Add a Bloom filter only when 404 miss-rate threatens origin DynamoDB capacity; decouple click analytics asynchronously unless strict attribution overrides tail latency.

  • Tier 1 (<100K rules): CloudFront Functions + KeyValueStore (~$18/mo list) — zero origin hops, sub-2 ms edge P99.
  • Tier 2 (10M+ rules): Edge TTL + Bloom filter guard + regional Redis + DynamoDB — absorbs 92% hits at edge and blocks scanner floods.
  • AI-Era Delivery Lens: Deterministic redirect-rule migrators and shadow-traffic verifiers now take hours to generate with AI. The real bottleneck is cross-team DNS cutover, slug governance, and rollback ownership.

1. Why Vanity URLs Differ From Generic Shorteners

A textbook URL shortener assumes opaque random keys (/a9Xk2q) with immutable targets. Enterprise vanity URLs (sujeet.pro/pricing, brand.co/launch-2026) invert the failure mode: rules change during campaigns, marketing teams collide on human-readable slugs, and broken redirects directly hit paid acquisition traffic.

Dimension Opaque Shortener Enterprise Vanity Router
Key Space & Collisions Base62 counter/hash; machine-owned Human-readable paths; cross-team namespace governance
Cache Invalidation Write-once; long immutable 301 Mutable targets; 302/307 + fast purge (<30 s SLA)
404 Miss Traffic Low except scrapers High bot/crawler probing — requires negative caching or Bloom guard
edge-redirector.ts · CloudFront Functions / Edge KV Fast Path TypeScript 
export async function handler(event: EdgeRequestEvent) {
  const slug = normalizeSlug(event.request.uri);
  const target = await edgeKv.get(slug); // ~1.2ms P99 at POP
  if (!target) {
    return { statusCode: 404, headers: { 'cache-control': 'public, max-age=60' } };
  }
  return {
    statusCode: target.permanent ? 301 : 302,
    headers: { location: target.destination, 'cache-control': 'public, max-age=300' },
  };
}

2. Protecting Origin Capacity With a Bloom Filter Guard

Once your catalog crosses 10M rules, storing every redirect inside an edge key-value store hits per-store size ceilings and replication lag. Moving misses to a regional cache + DynamoDB exposes the origin to 404 miss-rate storms from crawlers probing random paths.

Placing a compact, periodically snapshotted Bloom filter ahead of DynamoDB rejects ~99% of non-existent slugs in under 1 ms using ~14 MB of RAM for 10M keys — without touching origin read capacity units (RCUs).

3. AI-Era Delivery Economics & Organizational Bottlenecks

Five years ago, migrating 4M legacy Apache/Nginx redirect rules into an edge key-value router meant weeks of brittle regex parsers and manual QA. Today, generating a deterministic rule compiler, property-based loop detector, and shadow-traffic replay verifier takes an afternoon with coding agents.

Principal Engineer Reality Check

Writing the redirector service is rarely the schedule risk anymore. Your true critical path is cross-team DNS cutover windows, SEO equity sign-off (301 vs 302 semantics), namespace ownership between Marketing and Product, and ensuring on-call teams have an instant circuit-breaker back to origin when a bad bulk rule upload ships.

4. Cutover & Rollback Runbook

The migration is a sequencing problem, not a coding problem. Each step has an owner outside the platform team, which is exactly where timelines slip.

  1. Compile legacy Nginx/Apache rules into a typed rule table; fail the build on loops, chains > 2 hops, and shadowed slugs.Owner: Platform · ~1 day with AI-generated compiler + property tests
  2. Shadow-replay 7 days of access logs against the new router; diff status codes and Location headers.Owner: Platform + SEO · gate: < 0.01% mismatches
  3. Lower DNS TTL to 60 s at least 48 h before cutover; schedule the change window outside campaign launches.Owner: Network / DNS team · usually the longest lead time
  4. Weighted Route 53 shift 5% → 50% → 100% with an automated rollback on 5xx or redirect-mismatch alarms.Owner: On-call SRE · rollback must be one command, not a ticket
  5. Hand slug governance to a named owner (Marketing Ops) with a review queue; freeze bulk uploads without a dry-run diff.Owner: Marketing Ops · the step most teams skip

    AI-Era Build vs. Buy Lens

    Build vs. buy: owning Tier 2 costs list infra plus ~0.25 FTE of on-call and slug governance; buying is cheaper below ~20M redirects/mo. Coding agents now draft the rule compiler, Terraform modules, and synthetic load tests in days rather than weeks (assumption: ~2–3× faster first drafts), which lowers the build cost but not the run cost. Unless custom auth, zero-hop edge latency, or data residency forces ownership, the deciding line item is on-call and DNS cutover governance — not infrastructure.
